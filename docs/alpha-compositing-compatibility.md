# 蓝字亮边：透明合成兼容性记录

2026-10-02，用户提供的剪映实播截图中，黑色标题干净，蓝色标题、数字和眉题仍有浅白亮边。CSS 已经去掉描边和光晕，上一版也是从 Remotion 源码独立渲染，不能归因于多次修改导致像素偏移。

## 当前证据与限制

- 与用户截图相同的源帧 143（30 fps，4 秒 23 帧）做两种合成。将 straight alpha 的 RGB 错当成 premultiplied RGB 时，能复现蓝字亮边、黑字基本干净的特征；正确合成没有这个亮圈。这支持透明通道解释不匹配的判断，尚未直接测得剪映内部使用的公式。

- 兼容候选从新 PNG 做一次 RGB 预乘后编码 ProRes 4444，Alpha 保留。帧 172 对既有获准无边样片的 Alpha 掩码完全相同，预乘 RGB 可见区域平均误差 0.169，最大 4/255；帧 143 按预期合成时，蓝字边缘与正确参考平均差异约 0.485，最大 3/255。

## 编码决策

Remotion 的无损帧是权威输入，不在旧 MOV 上反复转码，也不把图形烧进底片。`scripts/encode-jianying-alpha.py` 只接受完整、从零起点的 PNG 序列，输出不覆盖已有文件。

先在 16 位 RGB 平面中将 RGB 乘以 Alpha，再编码 ProRes 4444，Alpha 使用 16 位。FFmpeg 8 有自动预乘转换，直接连接滤镜可能把预乘撤回，因此预乘后显式将 Alpha 解释标记设为 unknown；实测解码 RGB 与预期预乘值比较，不能只看命令是否返回成功。MOV 的容器标签不能代替编辑器实播验证。

PNG 的 8 位 Alpha 转成 ProRes 后可能产生 1/255 的归一化差异，因此传输校验对照的是原来获准的 ProRes 解码帧，不声称 PNG 与 MOV 的 Alpha 永远逐字节一致。真实编码测试同时检查 PNG→ProRes 的这项误差，以及两种 ProRes 的透明范围完全一致。

替换适配器新增 `alphaTransport=premultiplied-rgb`，只适用于已经明确选择无白边的样式。旧的严格原帧匹配仍是默认。兼容分支要求 Alpha 字节完全一致，RGB 的可见区域最大误差不超过 6/255、平均误差不超过 0.5/255；限值固定，不能由调用者放宽。判定按可见像素统计，避免大片透明区掩盖小范围白边。结果明确报告“字节不相等、传输等价通过、编辑器未验证”。

预乘兼容候选尚未通过剪映验收，不能升级成所有工具、所有编辑器的通用默认。ChatCut、浏览器和其他编辑器各自按实际透明解释方式选择编码，错误地多乘一次同样可能造成暗边。

## 目标编辑器验收

保存、正常退出剪映后，通过已有 Bridge 的 verifier/publisher 登记新副本；如果退出保存改变了源工程，基于最新保存状态重建副本。不能自动关闭剪映、覆盖原工程或绕过首页锁。

在剪映中打开新副本，对照 4 秒 23 帧的蓝字边缘，再播放入场、离场和第二模块。检查字体边缘、动画透明度以及独立轨道。如果仍有亮边，保留候选为失败/待诊断，不继续以“没有纯白像素”为修复依据；下一步做原 PNG、RGB 无损编码和目标编辑器导出的对照，以区分解码、透明解释和显示缩放。
