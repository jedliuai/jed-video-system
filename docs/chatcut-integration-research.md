# ChatCut 可以接入哪些环节

调查日期：2026-10-01。结论：优先把 ChatCut 作为口播精修、字幕和可编辑预览的可选后端；固定视觉组件继续由 Remotion 管理，本地剪映交付继续保留已有适配层。以下是接入建议，不代表已经完成或测试过 ChatCut 编辑。

## 本轮证据和连接状态

本机安装包 manifest 名称是 `chatcut-desktop`，显示名 ChatCut，版本 1.10.14，默认入口为连接 ChatCut Web。包名不能作为已经连接原生 Desktop 的依据。读取了基础说明、产品帮助、素材导入、Motion Graphics、口播剪辑、转录、验证、导出、多机位和问询表单等相关技能；并核对官方产品文档。

本轮可调用工具中未找到 ChatCut 工具；`codex mcp get chatcut` 返回 `No MCP server named 'chatcut' found`。这能确认当前会话没有可用的 ChatCut 编辑入口，但不能仅凭这两个现象断定用户未完成认证或整个插件安装失败。没有重复登录、安装插件、注册新服务、启动 Desktop、上传个人素材、创建项目或提交付费生成任务。

后续用户截图明确确认了 Codex 已安装并启用 ChatCut。这个安装状态成立，不能被当前旧会话缺工具或 CLI 查询失败推翻。补查的插件管理目录未能匹配该 marketplace 包，也不是未安装的证据；实际可调用状态仍需在加载工具的会话里确认。

官方说明工具在会话启动时加载，安装或更新后的原会话不会自动获得工具。实际试用应先在新的 Codex 会话确认 ChatCut 工具与托管连接状态，再按返回的连接错误处理；缺登记与缺认证是不同问题。官方版本页当前列出的 Agent Plugin 版本与本机包版本不完全一致，本报告以本机 manifest 描述安装包，以对应功能文档描述产品能力，不据此要求降级或重复更新。[Agent Plugin](https://chatcut.io/docs/agent-plugin)、[当前版本](https://chatcut.io/docs/releases)。

## 环节与推荐分工

| 环节 | ChatCut 的接入价值 | 与现有系统的分工 | 优先级 |
| --- | --- | --- | --- |
| 素材导入和时间线 | 建立可编辑项目，原视频、录屏、图层和音轨分别放置 | Jed 负责审核与约束；ChatCut 是一个可选编辑后端 | 高 |
| 转录和文字校正 | 对项目语音转录，修正字幕内容并组织脚本 | 本地 Video Use 保留；先比较识别、词边界和编辑质量，不双写同一份真值 | 高 |
| 口播精修 | 从脚本清理固定口癖、停顿；用脚本选择、删句和重排处理内容 | Jed 决定可删范围与候选审核；ChatCut 执行已确认的选择 | 最高 |
| 字幕 | 跟随脚本更新字幕，统一样式、关键词强调和导出 | 人工修正内容优先；现有剪映字幕仍用于本地交付 | 高 |
| 客户审阅 | 展示真实可编辑时间线，查看合成帧和分层内容 | 可补充当前 MP4 预览；不能替代剪映自身的应用验收 | 高 |
| Motion Graphics | 可编辑文字、颜色和数字；复用模板及项目视觉风格 | 固定组件留在 Remotion；ChatCut 做经适配的图形和视觉试验 | 中 |
| B-roll | 导入素材，或在获准后生成画面并安排上层轨道 | 始终服从分段策略；录屏默认复用用户明确的不加 B-roll 偏好 | 中 |
| 音效、配乐 | 搜索已有音效，必要时生成新音频并放入时间线 | 现有音效 skill 决定稀疏度、音量与触发点；ChatCut 是素材来源/执行选项 | 中 |
| 配音、数字人、翻译 | 后续制作不同语言或其他内容类型 | 当前真实口播无需启用，不自动替换用户声音 | 低 |
| 多机位同步 | 多份共同录制素材可能需要同步 | 仅在素材实际是多机位时启用；本机与托管支持需分别验证 | 条件启用 |
| 剪映工程交付 | Desktop 提供可编辑草稿输出 | 当前 Codex 托管插件不能直接算作已接入此功能 | 单独验证 |

产品支持项目素材、时间线、转录字幕、图形和生成媒体的编辑入口。[插件能力](https://chatcut.io/docs/agent-plugin)。音效和配乐应先复用已有素材，生成需要 credits，准确落点仍要做时间线调整。[音频说明](https://chatcut.io/docs/music-and-sound-effects)。

## 最有价值的第一步：口播精修

当前系统已经有逐词转录和时间计划编译器，但还没有停顿、口癖及重复句的候选审核。ChatCut 的脚本编辑工作流可以补这一段。

推荐流程：审核口播与录屏范围 → 复用已确认偏好 → 读取脚本 → 标出可删候选与原因 → 对改变意思或步骤的选择进行审核 → 先 dry-run → 应用脚本 → 更新时间映射 → 一次性刷新字幕 → 验证 → 再加入依赖语音时钟的动效与音效。

预检路径应把修改写入脚本，再使用 `apply_script` 的 `preview:true`。不要在预检前调用 `clean_script`，因为它立即写入，没有 preview 参数。这个 dry-run 验证编辑计划，不应被描述成已经能播放的合成视频预览；正式应用后仍需查画面和声音。已明确授权的机械处理无需再次请求确认。

`clean_script` 适合明确的口癖和停顿清理，不负责判断重复句、错误重说或叙事重排。后者需要读取脚本并做具体的语义选择。不能因为客户选择“精修”，就把这些更强的改写操作一并授权。口播+教程录屏还要检查操作画面与讲解是否保持同步。[口播剪辑](https://chatcut.io/docs/talking-head-edit)。

同轨 ripple 不会自动保证其他轨道同步。先完成讲述结构，再排字幕、B-roll、动效和声音；结构后改时必须重新检查所有依赖轨道。平滑音频也应在最终切点确定后处理。聊天记录、工具成功返回或 Script 文本本身，都不能替代合成画面的验证。

## 固定视觉如何与 ChatCut 共存

可以把现有 A 版约束映射为一个 ChatCut Design Style：直接叠在原画面上、没有深色底或大面积面板、统一字体与蓝色强调、避免遮脸、保留字幕区。风格指导后续图形，不会自动改造已有图形。[Design Styles](https://chatcut.io/docs/design-styles)。

ChatCut 的图形可以暴露文字、颜色、数字等可编辑属性，并保存为复用模板。[Motion Graphics](https://chatcut.io/docs/motion-graphics)。但它的 JSX 合约与本项目 TSX 不一致：使用注入的运行时、`item.props`、局部尺寸及独立的时间线放置，有字体和导出绘制限制。因此不能把现有 Remotion 文件直接整包导入，也不能承诺所有浏览器预览效果都会在导出中一致。

后续若适配，优先选一个低风险的两行重点文字组件，复用相同的品牌 token 和内容协议，建立 ChatCut 侧的实现。源代码通过当前工具的 inline JSX 接口提交，按插件技能规定操作；不复制第三方插件的源码或 skills 进本仓库。已接受的 A 风格不需要重新让客户选一次风格。

## 必须分清的交付边界

ChatCut 官方的可编辑剪映/CapCut 草稿交付属于 **ChatCut Desktop**。部分 ChatCut 专有属性不保证转移；图形可作为透明素材转移，仍要在目的编辑器检查。[剪映草稿说明](https://chatcut.io/docs/export-capcut-jianying)。

单个 Motion Graphic 可以导出带 Alpha 的 ProRes 4444 MOV，官方注明需要 Pro；这不是把整条时间线、字幕及普通视频一并导成透明文件。[透明图形导出](https://chatcut.io/docs/export-transparent-motion-graphics)。

因此接入方案应分开保存：

1. 本地路线：Video Use → edit-plan → Remotion → 现有 Jianying draft worker / Bridge → 剪映微调。
2. ChatCut 路线：原始素材 → ChatCut 脚本精修 / 字幕 → 可编辑时间线审阅 → 当前托管插件支持的输出。
3. 可选的 Desktop 交付：在用户明确选择后，验证 Desktop 草稿输出、图形属性退化和剪映版本兼容性。

这三条路线共享用户意图和约束，不默认持续同步两个编辑器。也不能把一条本地烧录字幕、混音完成的 MP4 当作 ChatCut 的主可编辑结果。

## 解耦建议

先保留现有核心协议：audit、项目答案、约束、transcript 和 edit-plan。将 ChatCut 放在外部 adapter 层，不让项目 ID、asset ID、item ID 或临时编辑器地址侵入通用计划。

建议未来拆成连接诊断、媒体映射、脚本编辑、字幕、图形、验证和交付七个小模块。每个模块独立报告可用能力，区分 hosted / desktop、支持的格式和所需权限；不以“装了插件”直接放行生产。

时间映射是接入关键：当前编译器只支持单源、单倍速、顺序且不重叠的源片段。ChatCut 若重排语句、保留同一句的多个实例、使用多源或变速，必须扩展通用计划或明确拒绝，而不是把输出秒数硬塞进源秒数。两个转录器的 word ID 也不能互换，需保留源哈希、转录版本、原词锚点及新的源到输出映射。

当前技能没有建立“直接导入现有 WhisperX JSON 即可免转录”的可用接口证据，不能承诺零成本复用。读回实际片段表时，保留 source offset、duration、输出位置和转录来源，按绝对帧边界统一取整，并避免越过源尾部。词时间仍是估计，需要对切点试听和保留自然余量。

## 应预置的客户问题

这些是未来接入点，本轮没有新增问询规则或自动默认值。

| 触发条件 | 应问或复用的选择 |
| --- | --- |
| 选择 ChatCut 路线 | 是否接受该路线所需的素材传输与服务处理；检查实际导入方式和服务需求 |
| 开始口播精修 | 只删口癖/长停顿，还是也处理重复句、错误重说或重排；有无必须保留的表达 |
| 口播与录屏混合 | 录屏操作等待是否保留；删掉语音后如何维持步骤与画面的同步 |
| 准备 B-roll | 仅口播还是其他指定段落；录屏“不加”的已有偏好直接复用 |
| 开始录屏标注 | 是否允许圈画、步骤标签或局部放大；不加 B-roll 不等于禁止标注 |
| 修正文本 | 只修字幕错字，还是也改变真实声音；后者另需明确选择 |
| 无法复用现有素材 | 是否允许付费生成，使用现有素材还是新生成；先确认小样和估算 |
| 交付阶段 | 需要 ChatCut 时间线、最终视频，还是可编辑剪映草稿；选择与当前后端能力匹配的路径 |

同机编辑器的 loopback 导入可以先在浏览器本地持久化素材，但后续同步、转录或云端功能仍可能需要上传。不能把这种导入方式宣传成整个 hosted 工作流完全离线。[产品形态](https://chatcut.io/docs/chatcut-products)，以及本机 `asset-import` skill 的导入与 readiness 规则。

## 建议验证顺序

先在新会话确认连接，再用非敏感的短样片做隔离试验：读脚本、删一个明确停顿、比较源/输出时间、刷新字幕、查看切点合成帧并试听。通过后才适配一个遵循 A 风格的图形。最后分别验证普通视频交付、独立透明图形和 Desktop 剪映草稿；不把一种输出成功当成其他输出已通过。

本轮完成文档研究和架构定位，ChatCut 转录、编辑、生成、导出、会员权限和目的编辑器兼容性均尚未实测。
