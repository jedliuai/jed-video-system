# 蓝字亮边要查合成，不能只查 CSS

这次用户又给了剪映实播截图：黑字已经干净，蓝字仍像带了一圈白边。我重新从 Remotion 渲染了完整的无损透明帧，做正确合成与错误透明解释的对照。错误解释能复现这圈亮边，所以目前最有力的原因是透明素材与编辑器的 Alpha 解释不一致。它不是反复挪动文字造成的累计像素偏移。

做了一版从新 PNG 生成的预乘兼容素材，并放进最新保存工程的独立副本。11 条轨道、29 个片段、42.6 秒和手动调整均保留，只替换两段 Remotion 透明动画。用户保存退出后，副本已通过原有 Bridge 登记到剪映首页，MCP 回读成功。实际剪映播放仍待验证。

值得记住：没有纯白像素，不等于合成后没有亮边。蓝字抗锯齿边缘带有半透明度，RGB 与 Alpha 的解释要配套。FFmpeg 8 还可能自动转换 Alpha，因此必须检查实际解码值，不能只相信滤镜名称。新增可复用 PNG 编码脚本，以及限定无边样式、要求透明掩码不变的机械传输校验，不拿一次技术兼容调整当成新的审美授权。

这次最大的坑是离线预览可以正常，而目标编辑器仍然异常。后续要始终分开记录浏览器帧、透明视频、实际剪映画面。Windows Computer Use runtime 仍不可用，用户截图是关键依据；未完成的目标应用验收必须如实留待验证。

185 项行为测试通过，包括真实 FFmpeg 的半透明蓝色编码测试。测试还暴露了 PNG→ProRes 的 Alpha 可能出现一个码值的归一化差异，所以“不变”的依据要写清：对照获准 ProRes 样片，不把所有编解码阶段混为一谈。原有严格样片匹配仍保留，预乘兼容分支不能放行新描边或新颜色。

一句话亮点：真正的画面质感，藏在从设计稿到剪辑轨道的最后一毫米里。
