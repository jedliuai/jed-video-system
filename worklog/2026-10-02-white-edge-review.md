# 文字白边先看图，再定厚度

今天把口播 Remotion 文字块的白边单独拿出来做了三档同帧对比：当前、稍薄、更薄。推荐稍薄这一档，但现在只是候选图，正式样式、透明视频素材和剪映工程都还没有改，等这次明确选定后再应用。

为什么要单独做这一步？用户喜欢白色包边带来的辨识度，只是觉得厚了一点。这个调整属于个人审美，不能把“效果不错”当成对新厚度的批准，也不能为了展示候选效果提前覆盖已经交付的可编辑工程。

记住几个点：实际白边来自半透明白色文字光晕，不是实线描边。这次只把模糊半径从当前的 4 像素试到 3 和 2 像素，白色透明度、向下偏移、字体、颜色和画面都保持一致。新增独立的 Remotion 预览入口，以原始素材第 180 帧做真实渲染，同时输出并排局部对比和三张完整画面。候选图片、渲染依赖和审核请求分别绑定文件哈希，三档都保持待确认状态，只能把实际选中的那一档记为认可。

一个容易踩的坑：用 Freeze 看第 180 帧时，预览 Composition 不能只有一帧，否则内部动画取到的帧会被限制，造成文字还没有出现；对比栏的 CSS 类名也必须互相隔离，避免后一栏的白边样式覆盖前一栏。

确认图片保留在本机 work 目录，公开仓库只同步预览代码和这份记录。剪映里已有保存后的多时间线结构，后续调整也要读最新工程并保留人工微调。

一句话亮点：让 AI 帮你调一圈白边，也先把选择权交回给你的眼睛。

## 后续纠正：先看对同一种白边

用户指出上面的三档图片与剪映效果不一致，随后发来了 00:00:05:22 的实际截图。截图里的白边是明显的实白轮廓，我前面展示的是柔和光晕；原来的 A/B/C 已撤回并标记为需要修改，没有任何一档获批。工程结构和素材哈希已读回，透明模块缩放为 100%、位置无偏移，但 Windows Computer Use 返回运行时不可用，无法自动看到剪映预览，尚不能确定该显示差异的底层原因。

用户随后倾向去掉白底和白色描边，也保留了“薄一点”的可能。这次用截图的同一时间点准备“无白边”和“极细白边”两个候选，关闭白色光晕；先渲染独立透明 ProRes MOV，再解码叠加当前工程里的真实底片，不再只依赖网页直接合成。预览不包含剪映原生字幕，并明确标注剪映显示尚未核对，只用于选定文字块的设计方向。正式默认值和当前工程继续保持原样。

总 skill 加上了这一条实用经验：微调现有工程时先校准用户看到的效果，不能让客户在两条尚未证明一致的显示路径之间确认厚度。未完成剪映显示核对，不能说“已与剪映一致”。
